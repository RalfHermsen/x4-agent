# Plan: from "it plays" to "it plays unattended"

Written 2026-10-18 after reviewing six days of live logs (1,511 cycles,
2026-08-19 to 2026-08-24). This is the brief for the next working session.
Read `CLAUDE.md` first, then `tasks/lessons.md`, then this file.

## What the log said

Of everything that reached the game, 3,511 commands were Python repricing and
roughly 900 were model decisions. The model's proposals were swallowed 757
times by the executor gates: about 220 because the ship was already busy
(the model re-proposes the same thing every cycle, because nothing tells it the
proposal was refused), about 160 because the sitrep was misread (a freighter
assigned to mine, a station of another faction), about 110 because the
extraction step invented placeholder codes (`MINER`, `other`, `N/A`). 397 of
the 1,511 cycles produced no command at all. Model time: 21 s per cycle on
average, 9 hours in total.

The two largest outcomes in the game, repricing (positive) and five scouts lost
in an afternoon (negative), both came from Python, not from the model.

Conclusion: the loop forgets and polls. Fix the loop before touching the model.

## Phase 1: offline work (no game needed)

Everything in this phase is testable against savegames on disk and an Ollama
host. **Nothing in this phase may send a command to the game.** Do not run
`run_host.py` at all; `agent.py`, `planner.py`, `evaluate.py` and the new
`score.py` are the tools.

Order matters: each item is used by the next.

### 1.1 Tests exist

There are none. Create `tests/` with pytest:

* A session-scoped fixture that parses one small save once
  (`save_007.xml.gz` in the profile folder found by `save_parser.documents_dir()`;
  23 MB, one station `KYV-745`, two ships, 200k Cr) and caches the parsed state
  as JSON under the pytest tmp path, so later tests do not pay 20 s each.
* A fake planner: fixtures that monkeypatch `planner.reason` and
  `planner.extract` to return canned text and a canned `PlannerResponse`, so
  `agent.cycle()` runs without a model. The whole loop becomes testable.
* `memory.STORE` must be redirected to a temp file in every test that touches
  memory. Never write to `logs/memory.json` from a test.

Done when: `py -3.14 -m pytest -q` passes and runs in under a minute after the
first parse.

### 1.2 Refusals feed back into the next cycle

`agent.cycle()` returns `skipped` (executor gates) and `rejected` (semantic
check) and then forgets them. The model never learns that its proposal was
refused and proposes it again three minutes later.

Requirements:

* `memory.record()` also stores the refused proposals of this cycle: action
  type, the reference fields, the reason, and a count of consecutive cycles the
  same proposal (same type and references) has been refused.
* `sitrep.build()` takes them and renders a section `# NOT DONE LAST CYCLE`,
  one line each, newest first, at most 10 lines, with the count when it is
  above one: `assign_ship NUH-323 -> KYV-745 mine: already busy with
  MiningCollect (refused 5 cycles running)`.
* `planner.REASON_SYSTEM` gets one sentence: a proposal listed there must not be
  repeated unless the situation it was refused for has changed.

Done when: a test runs `cycle()` twice on the same save with the fake planner
proposing a refused action; the second report contains the line with the count.

### 1.3 No model call when nothing changed

The host calls `cycle()` on a fixed interval. Add a fingerprint of the
planning-relevant state and skip both model calls when it is unchanged since
the last model call: the fleet roster, each ship's first order and target
sector, each own station's stock per ware rounded to 10 percent of capacity,
player money rounded to 5 percent, the failures list, and the standing goals.

* Python arithmetic (`repricing`, `focus_fleet`) still runs every cycle; it
  is cheap and deterministic.
* A model call is forced anyway after `X4_AGENT_MAX_QUIET` seconds (default
  1800), so goals do not go stale.
* The result dict says whether the model ran (`model_ran: bool`) and why not.

Done when: a test runs `cycle()` twice on the same save; the second run has
`model_ran == False`, zero model seconds, and still produces repricing commands.

### 1.4 The parser reads what expansion and purchase need

Add to the parsed state, with `explore_save.py census/find` to locate them:

* `player.blueprints`: the set of ware ids the player holds blueprints for.
* Per own station: storage capacity per type (container, solid, liquid) so
  that "full" becomes a fact rather than a share; the plot size; and for its
  build storage whether a construction vessel is assigned.

Done when: tests on the reference saves show non-empty blueprints, capacity
greater than or equal to stock, and plausible plot sizes. Document where each
lives in the save in `docs/savegame-format.md`.

### 1.5 Expansion gates and funding become arithmetic

* `executor.to_commands()` refuses `expand_station` when the blueprint for the
  production module (or the storage module the MD side would add) is not held,
  with the reason naming the missing ware. The ware-to-module mapping is one
  table in `executor.py`, kept in step with the `do_if` list in the MD cue;
  say so in a comment at both places.
* Funding: when a build storage of ours has builds queued or running and its
  account is below the cost of what it still has to buy (sum of buy offers,
  amount times price), emit `fund <station> <level>` with the smallest level
  (`low`/`mid`/`high`, see the MD cue) that covers the shortfall, never below a
  reserve of 20 percent of player money. Deterministic, every cycle, deduped
  through `memory.drop_repeats`.

Done when: unit tests with crafted states cover both.

### 1.6 An expansion is tracked until the station produces the ware

`memory.check()` judges four verbs; `expand` is not one of them, so a build
that never starts is invisible. Track each sent `expand` through stages, each
with a timestamp and a threshold after which it is reported as stalled:

1. planned (the command was sent)
2. build queued or running on the build storage (visible in the save)
3. construction vessel present
4. resources delivered (build storage cargo)
5. module present and the station produces the ware

A stalled stage goes into `failures` with the plain fact: `expansion of water
at KYV-745: planned 2h ago, no build started`. Say what is observed, not why.

Done when: a test feeds a sequence of crafted states and sees the stage
advance and the stall reported.

### 1.7 A scorecard

`score.py <save>`: game time, credits, stations, ships by role, idle ships,
ships failing their orders, builds in progress. `score.py --compare <a> <b>`:
the same side by side plus ships gone. This is the measure every later change
is judged by; without it "better" is an opinion.

Done when: it runs on every save in the profile folder without failing.

### 1.8 Model comparison: read, do not rerun

`out/cmp-gemma4/` and `out/cmp-gptoss/` hold one full advice per save for the
local model and for a hosted model reasoning with the local model translating
(`X4_EXTRACT_MODEL`). The summary tables are in the owner's private notes.
Read them, count per run: rejected, skipped, placeholder references, and
guideline violations visible in the reasoning (a freighter sent exploring, a
non-miner assigned to mine). Write the result as a short section in
`docs/contracts.md`. Do not rerun the comparison; it costs an hour of GPU.

## Phase 2: needs the running game

Each of these is a verb or a mechanism that can only be proven inside X4.
Every item here has, in this repo's history, taken a day and failed silently
at least once. Every Lua change needs a savegame reload, every MD change needs
`/refreshmd` in the in-game chat, and the evidence is in the logbook and the
next save. Without the harness in 2.0 that means a person at the keyboard:
**stop at the end of Phase 1 and hand over.** With the harness proven, the
session may continue on its own.

### 2.0 The harness: X4Mcp drives the game

[X4Mcp](https://github.com/eg3r/X4Mcp) (MIT) runs inside the game process as
an [X4Native](https://github.com/eg3r/X4Native) extension and exposes, over
HTTP on `127.0.0.1:7779`: `list_saves`, `load_game` (by filename or
`"latest"`), `is_game_loaded`, `execute_chat_command`, `shutdown_game`,
`capture_screenshot`, `log`, and a key-value stash. It reads no game state;
that is not what it is for. It is the hand on the keyboard.

**Installed and proven 2026-10-18**: X4Native v9.0.0-611726 and X4Mcp v1.0.6
under `extensions/x4native` and `extensions/x4mcp`, release zips unmodified.
The game is build 611726 (save header), exactly what that X4Native release
targets. Protected UI mode is off already (the pipe API needs it too).
Proven by hand: launch through Steam, `/health` answers about 45 s after
launch, `list_saves`, `load_game` of `save_007` (loaded in 45 s,
`is_game_loaded` true, X4Native fired `on_game_loaded` and
`on_universe_ready`), `shutdown_game`.

What the first launch taught:

* **X4Mcp 1.0.6 needs OpenSSL 3.** `x4native_x4mcp.dll` imports
  `libcrypto-3-x64.dll` and `libssl-3-x64.dll`, which the release does not
  ship; without them X4Native's log says `LoadLibrary failed (error=126)` and
  port 7779 never opens. Fixed by placing the two DLLs (OpenSSL 3.4.6) next to
  `X4.exe`: the application directory is on every DLL search path, the
  extension's own folder is not. Remove them to undo.
* **X4Native's log** is `x4native/x4native.log` in the X4 profile folder
  (next to the save folder). Read it before anything else when the port is
  silent.
* **Three hooks do not resolve on this build**: `X4_FrameTick`,
  `RadarVisibilityChanged_BuildEvent` and `EventQueue_InsertOrDispatch`
  ("missing RVA for this build?"). The last one is the typed MD-event
  mechanism, so **event-driven cadence cannot lean on X4Native events** on
  build 611726; the 2,065 exported functions do resolve. Item 1.3 stays a
  fingerprint in Python.
* `list_saves` returns names without extension (`save_007`, `autosave_02`)
  and includes the `*.replaced-*` copies. `load_game` takes `{"name": ...}`.
* Release 1.0.6 has nine tools; `capture_screenshot` is in the repository's
  June commits but not in that release. Do not plan on screenshots unless a
  newer release appears.
* The first launch after installing had a person present; later launches
  need nobody.

How it loads, from reading the shipped Lua: `ui.xml` runs `ui/x4native.lua`,
which `package.loadlib`s `native/x4native_64.dll`; that proxy copies
`x4native_core.dll` to `x4native_core_live.dll` next to it and loads the copy
(so a `_live.dll` appearing is the first sign it worked), then discovers
extensions with an `x4native.json`. X4Mcp's Lua side only calls game globals:
`LoadGame`, `GetSaveList`, `QuitGame`, `ExecuteDebugCommand`.

The server: `POST http://127.0.0.1:7779/mcp`, JSON-RPC 2.0, one response per
request, no session id, no auth (localhost only); `GET /health` answers
`{"status":"ok"}`. Methods: `initialize`, `tools/list`, `tools/call`. So a
Claude Code session can use the game's tools directly:
`claude mcp add --transport http x4 http://127.0.0.1:7779/mcp`.

Two things the shipped Lua revealed, both to verify in the game:

* `C.ReloadSaveList()` exists and is FFI-callable. That is the missing half of
  `tasks/lessons.md` L6a (the game never rescans the save folder): a verb
  that calls it would let the harness copy a baseline into a slot while X4
  runs.
* `load_game` matches the save by filename first, then by a substring of the
  displayed location or description. Name the baseline unambiguously.

Launching is the one thing X4Mcp cannot do, because it only exists once the
game runs. That is a script of ours, `launch_game.py`:

* `launch_game.py` starts `X4.exe` from the install folder (found through the
  Steam registry key, as `deploy_bridge.py` already does, or `X4_DIR`), with
  `-skipintro` and optionally `-logfile x4-agent.log`; Steam must be running.
  It then waits until `127.0.0.1:7779` answers, with a timeout, and prints
  whether X4Mcp is there. No X4Mcp: it says so and exits non-zero, because
  nothing after this step can be automated without it.
* `launch_game.py --stop` calls `shutdown_game` and waits for the process to
  exit. It never kills the process: a kill while the game is writing a save
  corrupts that save, and the test harness depends on saves.
* `launch_game.py --load <name>` is `load_game` plus a wait for
  `is_game_loaded`.

Once proven, the loop a session can run alone:

1. `launch_game.py`, which launches X4 and waits for port 7779.
2. `python deploy_bridge.py`, then `load_game <baseline>`. A save load is what
   a Lua change needs; `/refreshmd` through `execute_chat_command` is what an
   MD change needs; a full restart is `shutdown_game` and step 1 again.
3. Put the verb under test in `logs/outbox.txt`; the host sends it on the next
   heartbeat. Only `run_host.py` in advise mode plus the outbox: nothing the
   model proposes may reach the game during a test.
4. Ask for a save (the agent already does this through the pipe), parse it,
   and read the `[x4-agent lua]` and `[x4-agent]` logbook lines plus the
   state the verb should have changed. A screenshot is evidence too; a
   module floating beside the station is visible in one.
5. `shutdown_game` at the end, always, so the next run starts clean.

Baseline: copy `save_007.xml.gz` (one station, two ships, 200k Cr) to
`saves/baseline_small_station.xml.gz` (gitignored) and copy it into a save
slot before each run. The game only lists ten slots and reads the folder at
startup (`tasks/lessons.md` L6a), so copy before step 1.

**Open decision before any run that saves (owner's call):** the bridge's
`save` is `<trigger_autosave/>`, which overwrites the player's newest
autosave (L6e). Either the harness accepts that, with the saves it depends on
frozen in `saves/reference/` (done 2026-10-18: autosave_01 to 03, quicksave,
save_007), or a Lua verb `savegame <slot>` calls `SaveGame(slot, name)` into
one slot the owner gives up for the agent. The game's own autosave interval
writes autosaves either way during a long run. Until decided, harness runs
only launch, load and stop.

**Decided 2026-10-18: the agent's slot is `save_008`** (an early save of
the reference game, superseded; frozen copy in `saves/reference/`). The game's
own autosave stays on; the owner saves their own game by hand before a run.

Proven 2026-10-18, the whole loop with no one at the keyboard:
`launch_game.py --load save_007`, `run_host.py --no-plan`, `harness.py
signals` (verb out through the outbox, `savegame` into save_008, logbook
lines read back from the fresh save), `launch_game.py --stop`; autosaves
byte-identical before and after. Two faults found on the way and fixed:
every Lua command ran twice (L8e), and the no-plan host still asked for an
autosave (L8f).

### 2.1 `blueprint <ware> <faction>`: buying blueprints honestly

Read from the game's own `ui/addons/ego_detailmonitor/menu_trader_blueprintsorlicences.lua`
(extract it with `gamedata.py`). The UI does, in this order: check
`HasLicence("player", tradelicence, faction)`; licences have `minrelation` and
sometimes a `precursor`; price is the ware's `maxprice` for modules
(`avgprice * 10` for the other tags; corrected 2026-10-18 from the menu's
own code, lines 225-233); then
`TransferPlayerMoneyTo(price, station)` and only then `C.LearnBlueprint(ware)`.

**`LearnBlueprint` does not take money, and MD's `add_blueprints` neither.**
An agent that calls either without paying gets blueprints for free and is no
longer playing the same game. The verb must pay first, log the price and the
faction, and the next save must show the ware under the player's blueprints
and the money gone.

House rules, decided 2026-10-18:

1. Buying remotely is allowed, but only from a faction with a discovered
   station where one of our ships is docked.
2. The agent may buy licences itself.
3. Which faction is Python's choice, not the model's: first a faction whose
   licence we already hold; otherwise, among those whose reputation threshold
   we meet, the one where a ship of ours is docked or the nearest; ties go to
   the highest reputation. One primary faction; a second only for wares the
   primary does not sell. If nobody in reach sells it, no purchase, and the
   report says why.

**Lua side proven 2026-10-18** on the frozen 73-hour save, no one at the
keyboard: `dockat KTK-861 ZIR-755 teladi` docked a trader in about four
minutes; `blueprint module_tel_conn_vertical_01 KTK-861` paid exactly 73,227
Cr (the ware's maxprice) to the Teladi station and the blueprint is in the
next save; the same command again refused with "already ours". Verbs:
`dockat`, `docked` (lists our ships at foreign stations), `blueprint`.
Still to build: 2.1a and 2.1b below.

#### 2.1a The Python side: from a decision to a bought blueprint

* A scripted planner for in-game evals: `X4_AGENT_SCRIPT=<json>` makes
  `agent.cycle()` use a fixed `PlannerResponse` per cycle instead of the two
  model calls. Every in-game eval of a planner action from here on uses it,
  so a test never depends on talking a model into proposing something.
* A new action type `buy_blueprint` with `ware` (the module ware id) and
  `rationale`; `type` first, no defaults (docs/contracts.md). The extraction
  prompt lists it with its fields.
* The executor turns it into a job tracked in memory (`purchases`), one
  stage per cycle, like 1.6: choose faction, station and ship by the three
  house rules; send `dockat`; when the next save shows the ship docked at
  that station, send `blueprint`; when a later save lists the ware under the
  player's blueprints, done. Thresholds in game time: docking longer than
  30 minutes, or a purchase not in the save after two cycles, is reported as
  an observation.
* Choosing: candidate factions are the ware's `<owner faction>` entries in
  `libraries/wares.xml` (add `owners` and `licence` to `data/modules.json`);
  candidate stations are known stations of those factions; the ship is one
  of ours with a pilot that is not a miner, not the player-occupied ship, and
  preferably idle, then nearest by `data/sector_graph.json`. If nothing
  qualifies, no job, and the report says why.
* The Lua side's refusals reach the report. The parser reads the
  `[x4-agent lua]` logbook entries newer than the previous cycle's save time
  (the harness already has the regex) and puts them in `failures`. Without
  this a refusal such as "does not sell" is written in the game and never
  read by the agent.

Done when: crafted states walk the job from decision to done and report a
stall; a miner or the occupied ship is never chosen; a Lua refusal in a save
shows up in the next report; and one scripted run through the host in
execute mode on the frozen 73-hour save ends with the blueprint in save_008.

#### 2.1b Licences

* The parser reads the player's licences from the save (locate them with
  `explore_save.py`; expected under the player faction) and the player's
  faction relations, so "reputation allows it" is a number, not a guess.
* Lua verb `licence <type> <SHIP>`, bought at the faction whose station the
  ship is docked at, copied from the licence tab of the same menu:
  `GetOwnLicences(faction)` gives `type`, `price`, `minrelation`,
  `precursor`, `issellable`; refuse when `HasLicence` is already true, when
  `GetUIRelation(faction) < minrelation`, or when the precursor is not held;
  then `TransferPlayerMoneyTo(price, station)` and only then
  `AddLicence("player", type, faction)`. Logbook names faction, type, price.
* The blueprint job (2.1a) buys the ware's `tradelicence` first when the
  chosen faction lacks it and reputation allows; otherwise it picks another
  faction or reports. One primary faction (rule 3) keeps licence spend low.

Done when: crafted states show the job inserting the licence step only when
needed; in the game, one licence bought on the frozen save: money down by
the logged price, the next save lists the licence, the repeat is refused.

## Phase 3: the rest of the roadmap, as requirements

`docs/roadmap.md` listed these without requirements. Ordered by the
roadmap's failure modes: stalls, then bleeds, then gets shot, then growth,
then trust. Three roadmap items are already covered: losses (`check_fleet`),
event-driven cadence (1.3), and reloading without a restart (2.0, X4Mcp).
Primitives named here were read in the game's files on 2026-10-18 unless
marked plausible.

### 3.1 Stop buying what we make

A station that starts producing water keeps buying water, and pays NPCs for
what its own modules deliver. That is arithmetic, so Python, every cycle:

* For each own station, each ware in `production_queue` that still has a
  buy offer: `tradeware <station> <ware> buy off` (the Lua verb exists). Not
  for a ware the station also consumes unless it produces more than it uses;
  until recipe rates are read from `libraries/wares.xml`, only wares the
  station does not consume.
* Deduped through `memory.applied` (`tradeware` is already a configuration
  command). The report says which wares were switched.

Done when: a crafted state (a station producing and buying the same ware)
yields the command once and not again; in the game, the next save has no buy
offer for that ware on that station.

### 3.2 Full storage is a fact

The parser reads capacity (1.4) and the report still says shares.
`focus_fleet` releases the fleet when everything backs up equally, which is
right and useless: that station is short of transport.

* A ware table from `libraries/wares.xml` (`data/wares.json`: transport
  type, volume, average price), built by `gamedata.py --wares`.
* Per own station: fill per storage type as stock volume over capacity. The
  report prints it; above 90 percent it says so in `# ATTENTION`.
* `focus_fleet`: when no ware is the culprit and fill is above 90 percent
  across the board, report "transport shortage: N traders, M wares backing
  up, storage X% full" instead of releasing silently.

Done when: the fill on both stations of the frozen 105-hour save matches a
direct computation in the test; the crafted all-full state produces the
transport line; every other `focus_fleet` output is unchanged.

### 3.3 Threats in the report

`schemas.Threat` is never filled, so the combat chapter of the guidelines
cannot be reached. The save has what is needed: hostile ships and stations
carry `knownto="player"` when seen (121 Xenon M ships and 20 Xenon stations
known in the 105-hour save), and every object of ours carries `attacktime`
and `attackmethod`.

* The parser collects hostile objects known to the player per sector:
  Xenon and Kha'ak always, plus every faction whose relation to the player
  is hostile (relations read from the save; locate them). Counts by class.
* `Threat` per sector where we own something: counts by class, the most
  recent attack on one of ours in the last 30 game minutes, and a stated
  strength rule: any L or XL hostile is major, more than five M or S is
  moderate, else minor.
* `# THREATS` in the report, above `# ATTENTION`. The existing
  `assign_ship ... defend` is the first executable answer; 3.4 adds the rest.

Done when: on the 105-hour save the section's counts equal a direct count
from the file in the same test; a crafted attack 10 minutes old is listed, a
two-hour-old one is not; the fake planner can assign a fighter to defend in
response and the executor sends it.

### 3.4 Fleet roles

Only `defend` under a station exists. The MD action for the rest is
`set_subordinate_group_assignment` (object, commander, subordinategroupid,
assignment), read in `libraries/common.xsd`; the assignment names the game
uses (attack, interception, defence, and the others) must be read from the
game's libraries before use, not from memory.

* `assign_ship` accepts a ship of ours as `station_id`'s counterpart: a
  commander ship. Roles: `attack`, `intercept`, `defend`. MD finds the
  commander among our ships with the same whole-string matching it uses now.
* Python gate: only fighters and corvettes for attack and intercept;
  freighters and miners never. A commander must not be a subordinate of the
  ship being assigned.
* The parser reads a ship's commander and assignment from the save (the
  assignment check in `memory.check` currently guesses from idleness).

Done when: in the game, a fighter assigned to another of ours with
intercept shows that commander and assignment in the next save; the gates
refuse a freighter; `memory.check` judges assignments by the commander field.

### 3.5 Repeat orders

The model asks for them every cycle and they are the one thing in the
strategy document that stays out of reach. What is known: MD has
`set_current_loop_order` ("rotates the order indices in the loop"), and the
Lua side reads a ship's default order with `GetDefaultOrder(Order*,
UniverseID)`. How the UI turns a queue into a loop was not found yet.

* First, find it: the behaviour menu's "Repeat Orders" in the game's Lua
  (`menu_map.lua`, `menu_interactmenu.lua`), the loop flag on the order
  queue, and how it looks in a save (`<orders>` of a ship on a loop).
* Then a verb `repeat <SHIP> <buy station> <ware> <sell station>`: two
  trade orders in a loop. Python decides the route (best margin within
  reach, from the existing `trade_margins`); the model only asks for a loop.

Done when: on the frozen save a trader runs the loop twice (the queue in the
next saves shows the loop and the cargo moves); the executor gate refuses a
loop for a ship without a pilot or with the stations out of range.

### 3.6 Buy a ship

Read in the game's Lua: `AddBuildTask6(containerid, defensibleid,
macroname, UILoadout2, int64 price, CrewTransferInfo2, bool immediate,

### 3.7 Habitation and workforce

Workforce raises a station's output and the save records it:

* `expand <station> habitation`: one more branch in the MD cue, adding the

* The report prints workforce and the guidelines get one line on it.

Done when: workforce is read on the reference saves; the expansion is

### 3.8 The player outranks the agent

A button instead of a code comment. The Interact Menu API (installed,
`md/interact_menu_api.xml`) signals `Get_Actions` when a menu opens on an
object and takes `Add_Action` with a callback.

* MD: on `Get_Actions` for a ship of ours, add "Hand to agent" or "Take
  back" depending on its state. The callback writes `reserved <code> on|off`
  through the pipe (the `Write_Callback` cue exists) and a logbook line.
* Host and memory: `reserved` is a set of codes. The executor refuses any
  command for a reserved ship ("reserved by the player"), Python arithmetic
  included; the report marks the ship "(reserved by the player)".
* Default: every ship is the agent's, as today.

Done when: offline, a reserved ship never appears in commands and the
refusal names it; in the game, one click by a person (the only human step)
produces the pipe message in the host log and the logbook line, and the
next cycle leaves the ship alone.

### 3.9 An agent panel in the game

The Simple Menu API (installed, `md/simple_menu_api.xml`) builds options
menus from MD: `Register_Options_Menu`, `Add_Row`, `Make_Text`.

* After each cycle the host sends `panel clear` and one `panel <text>` per
  line: standing goals, commands sent, refusals, failures; at most 30 lines.
  MD keeps them in a list (no parsing needed: each line is one value) and
  renders them in an options menu named for the agent.
* Opening the menu writes one logbook line with the row count, so the
  harness can see it was shown.

Done when: offline, the host builds the panel lines from a cycle result; in
the game, after one cycle the menu shows them (one look by a person; there
is no screenshot tool in X4Mcp 1.0.6) and the logbook line is in the save.
